# 当前算法：反馈信息利用与指标设计

备份用说明。写的是**此刻代码实际在做什么**，方便以后把细粒度 repair kind 改成「候选引理 vs baseline」时对照，而不是对着记忆改。

求解器原始字段（Vampire `--statistics`、CVC5 difficulty 等）的词典见：

- [vampire_feedback.md](vampire_feedback.md)
- [cvc5_feedback.md](cvc5_feedback.md)
- 相对化门槛常数：[反馈指标与求解器配置.md](反馈指标与求解器配置.md)、[relative_metrics.md](relative_metrics.md)

本文不重复那些词典，只讲：**一次失败之后，系统记住了什么、用什么公式判「有没有进展 / 缺哪类引理」、这些信息怎么进下一轮 LLM 和路由。**

Vampire 路径在 `Mate_new_vampire.py`，CVC5 在 `Mate_new.py`。两边反馈结构和指标入口对称，下文用 Vampire 举例，CVC5 差异单独标出。

---

## 1. 先搞清三个词

系统要证的是 SMT 目标 \(G\)（公理 \(A\) + 否定后的 `check-sat`）。只有求解器返回 **`unsat`** 才算证出。失败时不会把 \(G\) 改掉，而是让 LLM 猜一组辅助引理 \(C\)，希望：

\[
A \land C \vdash G,\qquad \text{且每个 } c_i \text{ 自己也能被证出。}
\]

下面三个词在代码里经常一起出现，含义不同：

| 词 | 指什么 | 典型超时 |
|----|--------|----------|
| **直接 prove** | 当前目标单独交给求解器（首次检查，或有用性失败之后不再用这次比进度） | 正式超时，常见 60s |
| **有用性检查** | 把 LLM 给出的整组 \(C\) 加进公理，再证 \(G\) | 正式超时 |
| **sidecar / 诊断** | 有用性失败后，对「无引理 / 平凡对照引理 / 单条候选引理」各跑一次短诊断，用来**打分**，不决定成败 | 3s |

**Baseline（基线）**：当前目标、不加候选引理的那一次诊断（或首次 prove 缓存下来的统计）。问的是「求解器现在卡在哪」。

**Control（对照）**：在公理里加一条几乎无信息的平凡等式（例如某个 datatype 上的恒等），再跑 3s。用来挡住「随便加一条断言搜索体积都会变」的噪声。

**Candidate（候选）**：公理里只加**一条**非平凡引理，再跑 3s。问的是「加上这条之后，搜索有没有变得不那么卡住」。

## 2. 一次节点上，反馈从哪来

每个目标节点（根目标或子引理）跑 `prove_run`。失败后的状态写在该节点的 `failed_lemmas.json`。跨节点共享的是题级 **引理库**（已完全证出的公式，之后当公理注入）。

```text
ProveRun(G)
  │
  ├─ 首次 60s prove
  │     失败 → 缓存 baseline_diag，derive_repair_hints（尚无 C，单次 mix 来自 A→P）
  │
  ├─ 对 LLM 预算内每一轮 attempt
  │     选 prompt 模板 + solver profile（会读已有 hint / progress）
  │     LLM 生成 C
  │     过滤：语法、与 G 相同、未定义符号、（子节点）空输出+reason
  │     有用性：A ∪ 库 ∧ C ⊢ G ?（满超时，采 --statistics；不做 ucore 剪枝）
  │        ├─ 成功 → 整组 C 递归 ProveRun
  │        │           子节点 invalid → 父节点 invalid_lemmas
  │        │           子节点 useful 但自己证不出（情况 A）→ 只进库+树，不写 unproved / subgoal_failed
  │        └─ 失败 → 记 useless group
  │                  **mix 细 kind 来自这次 60s A∧C→P**（覆盖同名的首次 A→P hint）
  │                  可选 3s sidecar：只打 progress_lemmas / no_progress / partial_progress
  │
  └─ 预算用尽
        根节点 → failed
        子节点（depth≥1，诊断开）→ 再问一次 LLM：当前目标 invalid 还是 failed
```

第一次失败的 60s prove 和后面 3s sidecar **协议不同**（时长、是否 portfolio、是否采归纳焦点）。进度分只允许 3s 和 3s 比；细 kind 目前主要来自那次 60s。这是后面改 cand vs baseline 时最容易混的地方。

## 3. 反馈通道总表

这些块都会进**生成轮**的 user prompt（`format_solver_feedback_for_prompt`），除非表里写了「不进 prompt」。子节点**最终鉴定**那一次 LLM 只看义务树，不看本表其余块。

| 通道 | 写入时机 | 比较方式（现在） | 进生成 prompt？ | LLM 该怎么用 |
|------|----------|------------------|-----------------|--------------|
| `invalid_lemmas` | 引理本身被判定无效（未定义符号、与公理矛盾、子节点 `node_outcome=invalid` 等） | 无数值比较 | 是 | 不要再生成、不要削弱；用 reason 判断当前目标是否也无效 |
| `useless_lemma_groups` | 整组 \(C\) 有用性失败 | 无 | 是 | 不要原样再发同一组合；单条仍可能有用 |
| `progress_lemmas` | 有用性失败后的 3s sidecar，单条分 ≥ 0.5 | **已经是 cand vs control/baseline** | 是 | 搜索有动静，但**不等于**有用；优先 refinement，不要整组重发 |
| `repair_hints` 细 kind（`need_rewrite` 等） | 尚无 \(C\)：首次 60s \(A\to P\)；有 \(C\) 且有用性失败：这次 60s \(A\land C\to P\) | **单次 run 内部 mix**（不是 3s sidecar，也尚未做 cand−baseline） | 是（过滤后） | 「带着当前公理（和 \(C\)）证 \(P\) 卡住的形状」。有用性失败时，标题下列出当时的 \(C\)，再写 `Failed to prove the goal using the above lemmas and produced hints. Use these hints to choose the NEXT lemmas:` |
| `no_progress` / `partial_progress` | 有用性失败后，看 sidecar 有没有分 ≥ 0.5 的单条 | 由 progress 分间接得到 | 是 | 整组没证出；有/无单条进展 |
| `unproved_lemmas` | 情况 A（默认关写入） | 无 | 仅 flag 关且旧数据存在时 | 当前默认**不写** |
| 义务树 `obligation` | 每次 attempt 结束 | 无 | 是 | 上一轮拆分：proved 可复用，failed 可削弱，invalid 不可削弱 |
| 引理库 | 子引理完全证出 | 无 | 是（已在公理里） | 不要再生成等价公式 |
| routing 块 | probe / pair 历史 | profile 之间比对活动率 | 是（若开路由） | 给求解器配置，不是给引理形状 |
| `last_llm_reason` | 解析 `; reason:` | 无 | **不进** prompt | 子节点空输出时立刻停 attempts；最终鉴定解析 |

`repair_hint_for_prompt` 会丢掉：

- `kind == subgoal_failed`（当前默认也不再写入）
- `context` 以 `subgoal:` 开头的 ATP hint（子证明诊断，不灌回父节点）

保留的是**证明当前目标**时得到的 hint：首次 prove、有用性检查、以及 `baseline_goal` / `usefulness_check` 这类 context。

## 4. 指标设计：两套不要混用的尺子

失败之后，求解器统计被用成**两套独立指标**。它们问的问题不同，比较对象也不同。

```text
                    ┌─ 单次失败 run 内部的活动份额（mix）
                    │     → repair 细 kind：缺重写？缺归纳？卡在哪个项上？
求解器统计 ─────────┤
                    │
                    └─ 两次短诊断的相对增益（cand − ref）
                          → progress 分：这条引理有没有让搜索「不那么卡住」？
```

改 cand vs baseline 时，动的是**上面那条**（细 kind 的比较对象），不是下面那条（progress 已经是相对的）。

### 4.1 相对化原语（两套尺子共用）

实现：`solver_relative_metrics.py`。不再用 `INST > 50` 这种绝对个数，因为小题永远达不到、大题随便超过。

| 原语 | 直观含义 |
|------|----------|
| `log_gain(cand, ref) = ln(1+cand) − ln(1+ref)` | 相对增量。`0→3` 不会变成无穷大；`10000→10040` 几乎为 0。 |
| `activity_rate(count, elapsed)` | 每秒率。诊断时长略有差别时才能比。分母下限 0.2s。 |
| `is_relative_gain` | 高流量大约要 **+20%** log-gain，且增量超过 ref 的 2%；稀有事件大约 **+10%**，允许 `0→1`。 |
| `gain_score` | 大约翻倍 → 1 分，再封顶。 |
| 爆炸门 `EXPLOSION_LOG_GAIN ≈ ln 1.5` | 体积大约 +50% 且没有「产品」（改写/归纳/聚焦等）→ 扣分。 |

Progress 把这些原语用在**两次 run 的每秒率**上。Repair mix 把份额用在**同一次 run 内部**。

## 5. Progress：已经是 candidate vs baseline

入口：`analyze_lemma_progress` → `compute_progress_score`（`vampire_runner.py` / `cvc5_runner.py`）。

### 5.1 比什么

有用性失败后，最多对 3 条非平凡单条引理各跑 3s（跳过形如 `x=x` 的平凡等式）：

1. **progress baseline**：目标-only，3s（缓存键 `baseline_diag_short`）。
2. **control**：加平凡引理，3s（`control_diag`）。
3. **candidate**：只加这一条引理，3s。

打分时优先相对 **control**（没有 control 才相对 baseline）。问的不是「候选的绝对活动大不大」，而是「相对随便加一条断言，这条是否多出了有效产品」。

写入 `progress_lemmas` 的门槛：`_PROGRESS_SCORE_THRESHOLD = 0.5`。最多保留 6 条（按分排序）。

### 5.2 Vampire 计哪些信号

都是 **candidate 每秒率 vs 参照每秒率**：

| 信号 | 算进展的条件 | 分数 |
|------|----------------|------|
| `more_demodulations(+N%)` | 解调 + 等式重言式 过相对增益（高流量） | `gain_score`，帽 2.5；合成**一条**，不再把 demod 和 taut 各算一次 |
| `more_induction_activity(+N%)` | 结构归纳 + 整数区间归纳，稀有门 | 帽 2.0 |
| `lower_passive_ratio` | 被动/生成 < 0.7× baseline，且（有 control 时）< 0.9× control | +1.0 |
| `search_explosion(+N%)` | 子句率或 superposition 率 log-gain ≥ ln 1.5，且上面三条都没有 | 扣最多 1.5 |
| `weak_single_signal` | 独立通道 `strong < 2` 且没有归纳信号 | 正分 × 0.35 |
| `no_measurable_progress` | timeout/incomplete/unknown 且一条信号都没有 | 分 0，但会记这个标签 |
| `proved_goal` / `solver_error` | 短诊断直接证出 / 报错 | 100 / −10 |

整数归纳已经并进 `more_induction_activity`，不会在整数题上「进度面全是 0」。superposition **不加正分**，只参与爆炸体积。

### 5.3 CVC5 计哪些信号

同样是 cand vs control/baseline 的每秒率，另加 difficulty 的相对下降：

| 信号 | 含义 |
|------|------|
| `more_instantiations` / `more_conjecture_gen` | 匹配家族合成一条（INST 与 CONJ 取增益更大的那个标签） |
| `more_skolemize` | 稀有门 |
| `more_datatype_inference` | 稀有门 |
| `goal_difficulty_drop` / `axiom_difficulty_drop` | 本题内相对下降 ≥ 20% |
| `search_explosion` | conjecture-gen 体积涨、没有 skolem/datatype/difficulty/inst 产品 |
| `weak_single_signal` | 正分 × 0.4 |

### 5.4 和有用性的关系

Progress **不是**有用性证明。一条 lemma 可以：

- 分很高，但仍在失败的组合里（prompt 会标 `in_failed_group`）；
- 分不够 0.5，但以后换一组搭档就证出。

有用性成功时用 **unsat core** 裁掉没用上的引理名。那是剪枝，不是 progress 指标。

有用性失败时还会写一条总括 hint：

- 至少一条单条分 ≥ 0.5 → `partial_progress`
- 否则 → `no_progress`

这两条 kind **已经依赖 cand vs baseline**（有没有 progressive 单条）。它们和 `need_rewrite` 不是一类东西。

## 6. Repair 细 kind：现在是「这一次卡住的内部结构」

入口：`derive_repair_hints(result, context=...)`。

**输入是单次 `VampireResult` / `CvcResult`，没有 candidate，也没有 baseline 对照。** 看的是这一次搜索里「归纳 vs 重写」或「conjecture vs skolem vs inst」谁占主导，再加上 Vampire 的归纳焦点文本。

### 6.1 何时写入（粘性）

对当前目标：

1. **首次 60s prove 失败**（还没有 \(C\)）→ `_record_failed_prove_diagnostics` → `derive_repair_hints(..., context="initial_goal")`，并缓存 `baseline_diag`（之后不覆盖这份 60s \(A\to P\) 缓存）。
2. **有用性失败** → 用这次满超时 \(A\land C\to P\) 的统计 `derive_repair_hints(..., context="usefulness_check")`。有用性开 `--statistics` / difficulty / `--show_induction`，**不做 ucore**（证出则整组 \(C\) 都递归）。空统计不写 mix，以免覆盖已有 hint。
3. 3s sidecar **不再**写 `need_rewrite` 等细 kind，只打 `progress_lemmas` 以及 `no_progress` / `partial_progress`。
4. `record_solver_attempt` 仍可能把同一次有用性的 hint kind 记进 **routing pair 历史**。

存储：`_compact_repair_hints` 对每个 `kind` **只留最后一次**。因此有用性失败后，同名细 kind 会被 \(A\land C\to P\) 的 mix 覆盖；LLM 下一轮看到的是「带着这组 \(C\) 证 \(P\) 怎么卡」，不再是第一次直接 prove。

有用性成功不给父节点写 mix。仍是单次 mix，不是 cand−baseline。

### 6.2 Vampire mix（同一次计数的份额）

记：

- `dem` = 前向+后向解调次数  
- `ind` = 结构类归纳 + 整数区间归纳  
- `mix = ind + dem`

每条 hint **一个不等式**，允许同时给出（不再 `if/elif` 掐掉另一条）。

| kind | 条件（当前） | 告诉 LLM |
|------|----------------|----------|
| `induction_stuck` | 有 induction focus 或压缩后的 schema | 卡在这些项/图式上，写构造子等式桥；无数值门 |
| `need_rewrite` | `ind > 0` 且 `dem/ind < 8` | 归纳已经在动，解调相对太少 → 缺 IH 下能改写的等式 |
| `need_induction_lemma` | `ind/mix < 0.15` 且整数归纳不占主导 | 归纳占总活动不到 15% → 要加强/一般化归纳命题 |
| `need_arithmetic_lemma` | 整数归纳 / 总归纳 ≥ 0.70 | 别写 ADT 构造子，写递推/单调/界 |
| `need_directed_rewrite` | superposition / (demod+taut) ≥ 8 | 等式在叠加但不化简 → LHS 对准目标子项 |
| `induction_depth_limit` | `MaxInductionDepth ≥ 2` 且未证出且 `ind > 0` | 加深搜索没用，要强化引理 |
| `timeout` | 状态 timeout **且上面一条都没有** | 兜底 |

`strength` 来自门槛越界程度（`gate_overshoot`），给两类 prompt 模板同时触发时的抽样权重。

归纳焦点 `induction_focus` 会进 prompt（最多 4 条展示）。这是文本信号，不是 cand vs baseline。

### 6.3 CVC5 mix 与 difficulty

| kind | 条件（当前） | 告诉 LLM |
|------|----------------|----------|
| `high_difficulty_assertions` | 本题正 difficulty 的中位数及以上公理，或目标片段 | 在难公理和目标之间搭桥 |
| `need_stronger_lemma` | `skol/conj ≤ 0.05`（conj>0） | 猜想生成多、skolem/归纳强化少 |
| `need_rewrite` | 已 skolem，且 inst 占 (skolem+inst) < 0.75 | 匹配/重写跟不上 |
| `timeout` | timeout/unknown 且上面都没有 | 兜底 |

Hard axioms 是**本题内分位**，不是全局 `difficulty ≥ 3`。

### 6.4 用一个数字例子看清「单次 mix」和「相对增益」的差别

假设首次 60s：`ind=40, dem=20` → `dem/ind=0.5 < 8` → 写下 `need_rewrite`（归纳在动、重写少）。

LLM 随后给出引理 L。3s sidecar：

- baseline：`ind=2/s, dem=1/s`
- candidate：`ind=2.1/s, dem=3/s`

Progress 会看到 `more_demodulations`（重写率相对涨了），可能写入 progress lemma。  
但 sticky 的 `need_rewrite` **不会因为 L 而更新**——它仍来自第一次 60s 的 mix。

以后若改为 cand vs baseline，同一次失败更合理的细 kind 应是：相对 baseline，demod 份额升了 → 不必再喊 `need_rewrite`；若 induction 份额升而 demod 仍低，才喊 `need_rewrite`。

## 7. 这些信息怎么被用掉

不只进 LLM 文本。同一份 `repair_hints` / `progress_lemmas` 有三个消费者。

### 7.1 生成轮 prompt（主路径）

`create_prompt(..., diagnosis_only=False)` 拼：

1. 模板（等式推理 / 项重写，或 naive）
2. SMT 正文
3. §3 各块（invalid → useless → progress → unproved → routing → repair → 库+树）
4. 若 `depth≥1` 且诊断开：生成用鉴定后缀（可以空输出 + `; reason:` 宣布当前目标无效）

### 7.2 最终鉴定 prompt（只在子节点预算用尽且有可用树时）

`diagnosis_only=True`：SMT + **义务树** + `FINAL_DIAGNOSIS_PROMPT_SUFFIX`。不要库、不要 invalid/progress/repair/routing。本节点没有 `last_normal_tree`（只有 empty / invalid / useless）时**不调用**这次 LLM，节点保持 `failed`（生成轮已经判过 invalid 的除外）。

输出：`invalid` + reason → 本节点 `node_outcome=invalid`（`source=llm_final`）；`failed` / 解析失败 → 保持 `failed`。根节点不做这一步。子节点 invalid **不会**自动让父节点 invalid，只会把那条引理记进父的 `invalid_lemmas`。

### 7.3 Prompt 模板选择（`PROMPT_RETARGET`）

两类模板，名字与文件内容一致：

- `prove_prompt_equational_reasoning`：等式归纳推理。走 IH、为归纳步补桥、写更强的归纳假设或交换律一类引理。
- `prove_prompt_term_rewrite`：按目标（或子项）做定向重写，把模式换成更简单的形式，必要时再加强前提。

hint 族按「求解器缺什么引理」对齐到**会写出那类引理的模板**，不要按文件夹名字的英文对调：

| hint 族 | kinds | 起始模板 |
|---------|-------|----------|
| 重写 | `need_rewrite`, `induction_stuck`, `need_directed_rewrite` | `prove_prompt_term_rewrite` |
| 一般化 / 归纳 | `need_induction_lemma`, `need_stronger_lemma`, `need_arithmetic_lemma`, `induction_depth_limit` | `prove_prompt_equational_reasoning` |

没有 hint 时保持论文顺序（先 equational）。两类同时在 hints 里时，按各 hint 的 `strength` 抽样：\(P(\texttt{term\_rewrite})=\texttt{rewrite}/(\texttt{rewrite}+\texttt{generalize})\)。连续两次 empty / invalid / useless 才切到另一族（与 hint 无关，只是换搜索语言）。hint 族集合变了则重新按上表选择；若已经在对应模板上则保持。

`search_explosion` / `timeout` / `high_difficulty_assertions` **不**进入 prompt 族，只影响求解器 profile。

因此：**细 kind 从「单次 mix」改成「cand vs baseline」之后，模板选择也会跟着变。** 这是预期效果，改的时候要一起看 `solver_routing.py` 里 `_REWRITE_HINTS` / `preferred_prompt_for_hints` / 抽样函数。

### 7.4 Solver profile 排序

静态理论分流（ADT / 整数 / 混合）之后，hint kind 会 boost 某些 named profile（例如 `need_arithmetic_lemma` → 整数归纳配置）。3s progress 信号另走 `apply_progress_routing`：`partial_progress` / `more_demodulations` 等倾向保持当前 profile；`no_progress` / `search_explosion` 倾向换下一个。

Probe utility（2s，profile 之间比活动率）只用于排序候选配置，不写进引理进度分。

## 8. 子目标相关反馈（与 ATP 指标正交）

这些不是求解器 mix，但同属「失败后记住什么」。改 cand vs baseline 时一般**不要动**。

| 情况 | 当前处理 |
|------|----------|
| 子节点 SAT / 生成空输出且有 invalid reason / 最终鉴定 invalid | 本节点 `invalid`；父节点把对应引理写入 `invalid_lemmas` |
| 子节点有用但递归证不出（情况 A） | 已证兄弟进**库**；失败边进**树**（failed）。默认不写 `unproved_lemmas`、不写 `subgoal_failed` hint、不把子节点 3s 诊断抄到父 prompt |
| `UNPROVED_NOT_INVALID=off` | 情况 A 仍会把该引理标进父节点 invalid |
| 未定义符号 | 引理 invalid（`undefined_symbol:...`），不是把根节点标成 invalid |
| 并行子目标 | 先等飞行中的兄弟；取消的节点若自身 `node_outcome=invalid` 仍按 invalid 记账 |

树状态 `tree_status_from_child_data` 只看**这个子节点自己**的 `node_outcome` / SAT，不把更深层孙节点的 invalid 继承成自己 invalid。

## 9. 以后改成 cand vs baseline 时建议对照的清单

目标（此前讨论、**尚未实现**）：有用性失败时，细 kind 应描述「加了候选之后 mix 相对 baseline 怎么变」，而不是「第一次 60s 目标自己的 mix」。没有候选诊断时，再回退到当前的直接 prove mix。

| 项目 | 现在 | 改时建议 |
|------|------|----------|
| `compute_progress_score` | 已是 cand vs control/baseline | **保持**。不要把细 kind 塞进这个函数混成一个分数 |
| `no_progress` / `partial_progress` | 已由「有无分 ≥ 0.5 的单条」决定 | 可保持；或改成由新细 kind 是否为空来决定，二者选一，避免两套「有没有进展」 |
| `derive_repair_hints(单次 result)` | 首次 60s 的 mix + 焦点 | 仍用于：**无 sidecar 时的回退**（首次 prove、没有候选、progress 关闭） |
| 有用性失败后的细 kind | 不根据 cand 更新 | 在 `analyze_lemma_progress` 里，用 **同一套 3s cand 与 3s baseline 的 mix 差** 映射到 `need_rewrite` 等；有多条候选时要先约定：按最高分那条、还是按「任一条触发」、还是按平均份额 |
| 比较协议 | 60s mix vs 3s 进度 | 新细 kind 必须 **3s vs 3s**，不要拿 60s baseline mix 去减 3s candidate mix |
| Control | 只用于 progress 分 | 细 kind 建议仍相对 **目标-only baseline**（问「引理改变了目标搜索结构没有」）。Control 是噪声地板，不适合当 mix 的「缺什么」参照 |
| `induction_stuck` / focus / schema | 来自那次失败 run 的文本 | 焦点可以继续用 baseline（目标卡在哪些项）；若 candidate 的 focus 变了，可当作「引理把归纳推到了新项」——要单独设计，不要和 mix 份额绑死 |
| CVC5 `high_difficulty_assertions` | 单次 difficulty 列表 | 相对化版本已有：`goal_difficulty_drop` 在 progress 里。细 kind 可改为「candidate 相对 baseline 难度没降」才保留 hard-axiom 列表 |
| Sticky `_compact_repair_hints` | 每 kind 留最后一次 | 有用性失败后写入的新 kind 会覆盖首次 prove 的同名 kind。若希望「无候选时仍显示入口 mix」，需要分 `context` 或分字段，不要静默覆盖后找不到回退 |
| Prompt 过滤 | 丢掉 `subgoal:*` | 继续丢掉子证明诊断。新细 kind 的 `context` 建议用 `usefulness_sidecar` 之类，不要写成 `subgoal:` |
| 路由 / 模板抽样 | 读细 kind 名字 | 名字保持不变（`need_rewrite` 等），只改**何时写下这些名字**，路由表可不动 |
| `FEEDBACK_PROGRESS=off` | 无 sidecar | 细 kind 仍来自 60s \(A\to P\) / 失败的 \(A\land C\to P\)；只是没有 progress lemma 和 `no_progress`/`partial_progress` |
| `FEEDBACK_REPAIR_HINTS=off` | 不写 hint | 与现在相同 |
| 义务树 / 库 / invalid / 最终鉴定 | 与 ATP mix 无关 | 不要绑进 cand vs baseline |

### 9.1 一份可用的映射草稿（未实现，仅备忘）

对 Vampire，在 3s baseline 与 3s candidate 上都算 `ind_share`、`dem/ind`，然后例如：

- baseline 已 `need_rewrite`，candidate 的 `dem/ind` **相对升高越过门** → 不再写 `need_rewrite`（引理已经在补重写）
- candidate 的 `ind_share` 升、`dem/ind` 仍低于门 → 写 `need_rewrite`（归纳更热闹但还是缺桥）
- candidate 的 `ind_share` 相对 baseline **下降**且低于 `INDUCTION_SHARE_MAX` → 写 `need_induction_lemma`
- 体积相对涨且无产品 → 可写 `search_explosion` 进 hint（现在爆炸主要在 progress 信号里）

CVC5 同理：看 `skol/conj`、`inst/(skol+inst)` 相对 baseline 的方向，而不是 candidate 绝对份额。

阈值常数仍用 `solver_relative_metrics.py` 顶部那些；改的是**比较对象**，不必先重标定绝对数。

## 12. 一句话对照

- **Progress**：这条候选引理相对对照/基线，搜索有没有更像在干活（已是 cand vs baseline）。
- **Repair 细 kind（现在）**：当前目标这一次失败 run 内部，归纳和重写谁多谁少、卡在哪个项上（单次 mix，sticky）。
- **义务树 / 库 / invalid**：证明义务怎么拆的、哪些公式已是公理、哪些猜想根本不是定理（与统计指标无关）。
- **下一步**：有用性失败时，让细 kind 也改看 3s cand vs 3s baseline 的 mix 变化；没有 sidecar 时继续用现在的直接 prove mix。
